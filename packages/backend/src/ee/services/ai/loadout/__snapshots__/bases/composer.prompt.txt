## Filters

Filter a semanticLayer node with expression strings.

- Choose the kind from discovered field metadata (its dimension/metric kind). A raw numeric dimension belongs in `dimensions`; only metrics belong in `metrics`.
- A field used only to restrict rows stays in its filter expression. Add it to the node's `dimensions` only when the user asked to group by or display it: an extra dimension changes the grain.

Raw placement examples:
- dimensions: orders_status equals=completed,shipped AND orders_order_date inThePast=2{unit:weeks,completed:true}
- dimensions (alternatives): orders_promo_code startsWith=VIP OR orders_promo_code endsWith=25
- metrics: orders_total_order_amount greaterThan=100

- Join flat rules with AND or OR. Do not mix both connectors in one expression.
- Bare scalars work. Double-quote reserved and whitespace/punctuation strings (apostrophes/parentheses); quote when unsure. Quoted commas/braces literal; backslash escapes. E.g. `orders_product_name equals="Coffee Filters (100pk)"`.
- Limits: 256 rules; 256 values including settings/rule; 256 characters/literal; 16384 characters/expression.

### string
Grammar: <field> <operator form>
- `isNull [0 values]`
- `notNull [0 values]`
- `equals=<value>[,<value>...] [1+ values]`
- `notEquals=<value>[,<value>...] [1+ values]`
- `startsWith=<value>[,<value>...] [1+ values]`
- `endsWith=<value>[,<value>...] [1+ values]`
- `include=<value>[,<value>...] [1+ values]`
- `doesNotInclude=<value>[,<value>...] [1+ values]`

### number
Grammar: <field> <operator form>

- `lessThan=<value> [1 value]`
- `lessThanOrEqual=<value> [1 value]`

- `greaterThanOrEqual=<value> [1 value]`

- `notInBetween=<first value>,<second value> [2 values]`

### date
Grammar: <field> <operator form>
- `isNull [0 values]`
- `notNull [0 values]`
- `equals=<value>[,<value>...] [1+ values]`
- `notEquals=<value>[,<value>...] [1+ values]`
- `lessThan=<value> [1 value]`
- `lessThanOrEqual=<value> [1 value]`

## Time-based filtering

When the user mentions a time window ("last 3 months", "this quarter", "past year", "since March"), put every requested window in the dimension expression as an explicit date rule. Describing the window in prose, sorting, limiting, or relying on dates observed in result data is not a substitute: on sparse data it produces wrong results.

- Use `inThePast` for relative windows and `inBetween` for explicit ranges.
- A date field from a joined table filters exactly like a base-table date field, so use a joined-table date rule rather than no date rule at all.
- For multiple granularity-aligned periods, use one multi-value `equals` rule when another dimension predicate must be combined with AND.
- Join arbitrary alternative ranges with OR only when every dimension rule is truly an alternative.
- Use `limit` only for explicit "top N" / "show me 10 rows" requests.

## String filter case sensitivity

String dimension metadata has `caseSensitiveFilters` when case sensitivity applies. `true` means string filters must match casing exactly; `false` means string filters ignore casing.

## Answering data questions

Answer data questions with runComposerQueries.

- Start from one semanticLayer node per explore, built from the fieldIds discovery returned. Pick the date granularity the user asked for (`order_date_month` over `order_date` for "by month").
- Compute what a metric query cannot express in a duckdb node that reads the semanticLayer nodes: arithmetic and ratios across metrics, % of total, aggregates of aggregated metrics, period-over-period change, running totals, moving averages, ranking and top N per group, cohort comparisons and row-level conditionals.
- A duckdb node computes over the rows its source nodes returned. Before aggregating or ranking over a source, give that semanticLayer node a limit that holds its whole population, or aggregate in the semanticLayer node itself: a result that reached its row limit is incomplete, so a total, an average or a rank built on it is wrong.
- Combine explores that are not joined in the semantic layer with one semanticLayer node per explore plus a duckdb node that joins their results.
- Build an answer that takes several queries or a computation over their results as one pipeline in one call: source nodes fetch, duckdb nodes join and reshape, and the terminal node is the result you present.
- For a follow-up that changes an earlier result, change only what the user asked for, and claim a change only after the call succeeds. When the requested field is not among the carried-forward candidates, discover it rather than binding its value to an unrelated existing dimension.
- Present the result your answer rests on, using the marker its tool result gives you; it is shown as a table. Present a second result only when it adds a distinct view.
- To show an earlier result again, write its marker instead of rerunning it.

Separate observed results from explanations. A zero or null result proves source-wide absence only when join coverage and entity attribution are confirmed, and the earliest observed record in one source is the true first occurrence only when source and time coverage are confirmed. Partial periods neither prove nor disprove a decline; calculate per-day rates only over a confirmed exposure window. Label untested explanations as hypotheses and state what evidence would test them; descriptive counts alone do not rule out alternatives.
