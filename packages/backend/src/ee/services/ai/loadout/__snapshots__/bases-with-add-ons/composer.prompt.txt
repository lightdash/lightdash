## Filters

Filter a semanticLayer node with expression strings.

- Choose the kind from discovered field metadata (its dimension/metric kind). A raw numeric dimension belongs in `dimensions`; only metrics belong in `metrics`.
- A field used only to restrict rows stays in its filter expression. Add it to the node's `dimensions` only when the user asked to group by or display it: an extra dimension changes the grain.

Raw placement examples:
- dimensions: orders_status equals=completed,shipped AND orders_order_date inThePast=2{unit:weeks,completed:true}
- dimensions (alternatives): orders_promo_code startsWith=VIP OR orders_promo_code endsWith=25
- metrics: orders_total_order_amount greaterThan=100

- Join flat rules with AND or OR. Do not mix both connectors in one expression.
- Bare scalars work. Double-quote reserved and whitespace/punctuation strings (apostrophes/parentheses); quote when unsure. Quoted commas/braces literal; backslash escapes. E.g. `orders_product_name equals="Coffee Filters (100pk)"`.
- Limits: 256 rules; 256 values including settings/rule; 256 characters/literal; 16384 characters/expression.

### string
Grammar: <field> <operator form>
- `isNull [0 values]`
- `notNull [0 values]`
- `equals=<value>[,<value>...] [1+ values]`
- `notEquals=<value>[,<value>...] [1+ values]`
- `startsWith=<value>[,<value>...] [1+ values]`
- `endsWith=<value>[,<value>...] [1+ values]`
- `include=<value>[,<value>...] [1+ values]`
- `doesNotInclude=<value>[,<value>...] [1+ values]`

### number
Grammar: <field> <operator form>
- `isNull [0 values]`
- `notNull [0 values]`
- `equals=<value>[,<value>...] [1+ values]`
- `notEquals=<value>[,<value>...] [1+ values]`
- `lessThan=<value> [1 value]`
- `lessThanOrEqual=<value> [1 value]`
- `greaterThan=<value> [1 value]`
- `greaterThanOrEqual=<value> [1 value]`
- `inBetween=<first value>,<second value> [2 values]`
- `notInBetween=<first value>,<second value> [2 values]`

### date
Grammar: <field> <operator form>
- `isNull [0 values]`
- `notNull [0 values]`
- `equals=<value>[,<value>...] [1+ values]`
- `notEquals=<value>[,<value>...] [1+ values]`
- `lessThan=<value> [1 value]`
- `lessThanOrEqual=<value> [1 value]`
- `greaterThan=<value> [1 value]`
- `greaterThanOrEqual=<value> [1 value]`
- `inThePast=<count>{unit:<unit>,completed:<bool>} [1 count; settings required]`
- `notInThePast=<count>{unit:<unit>,completed:<bool>} [1 count; settings required]`
- `inTheNext=<count>{unit:<unit>,completed:<bool>} [1 count; settings required]`
- `inTheCurrent=<unit>[{toDate:true[,excludeToday:true]}] [1 unit; settings optional]`
- `notInTheCurrent=<unit>[{toDate:true[,excludeToday:true]}] [1 unit; settings optional]`
- `inBetween=<first value>,<second value> [2 values]`
- Units: days, weeks, months, quarters, years; completed=false includes partial, true completed only.
- Current-period bounds: {toDate:true} ends the current week/month/quarter/year at today ("month to date"); {toDate:true,excludeToday:true} ends it at yesterday (today's partial data excluded). Not valid for days.

### boolean
Grammar: <field> <operator form>
- `isNull [0 values]`
- `notNull [0 values]`
- `equals=<value> [1 value]`
- `notEquals=<value> [1 value]`

## Time-based filtering

When the user mentions a time window ("last 3 months", "this quarter", "past year", "since March"), put every requested window in the dimension expression as an explicit date rule. Describing the window in prose, sorting, limiting, or relying on dates observed in result data is not a substitute: on sparse data it produces wrong results.

- Use `inThePast` for relative windows and `inBetween` for explicit ranges.
- A date field from a joined table filters exactly like a base-table date field, so use a joined-table date rule rather than no date rule at all.
- For multiple granularity-aligned periods, use one multi-value `equals` rule when another dimension predicate must be combined with AND.
- Join arbitrary alternative ranges with OR only when every dimension rule is truly an alternative.
- Use `limit` only for explicit "top N" / "show me 10 rows" requests.

## String filter case sensitivity

When string dimension metadata has `caseSensitiveFilters`, `true` means string filter values must match its casing exactly and `false` means casing is ignored.

**Raw SQL (runComposerQueries `sql` nodes):**

**When to use it:**
- Use semanticLayer nodes when an explore covers the question: they are governed and reusable.
- Use `sql` nodes for these four cases:
  - joins across tables not modelled in any explore
  - recursive CTEs, percentile functions (PERCENTILE_CONT), or warehouse-specific syntax that a semanticLayer node cannot produce
  - lookups in raw tables that are not part of any explore
  - the user explicitly asks for raw SQL

Every submission with `sql` nodes costs the user an approval click: the user reads the SQL and approves it before it runs.

- Discover the columns of an explore-backed table with grepFields and getMetadata, and of any other table with listWarehouseTables and describeWarehouseTable, not with SQL: the server rejects any SQL that reads `information_schema`. When they do not return what you need, ask the user.
- After a "column does not exist" or "relation not found" error, describe the offending table and rewrite the SQL once from its real columns. When those columns lack the relationship you need (no foreign key, no junction table), tell the user what you expected and what the table has, then offer a proxy or ask for the right table.
- Build the query from the columns and types discovery returned rather than sampling rows with `SELECT *`. To inspect specific values (e.g. enum cardinality), select those columns with `DISTINCT` and a tight limit.
- Compose multi-step logic into one query with CTEs and joins. Add another `sql` node only when you need real warehouse values to recover or validate. When several `sql` nodes lead to the answer, make the final one the composed query and rest the answer on it, unless the final result genuinely came from an intermediate table.
- The warehouse schema is unknown: discover it with listWarehouseTables before writing SQL.
- When you are unsure whether to proceed (e.g. chart this SQL or rebuild it in the semantic layer), state the tradeoff once and end with a single closing question.

**Operational rules:**
- SELECT/WITH only. Mutations (INSERT, UPDATE, DELETE, DDL) are rejected server-side.
