# Exploratory vs presented results in agentic data-analysis tools

Question: when an agent runs several queries/charts, how do tools decide which get shown to the user vs kept as internal scratch? Context: Lightdash AI agent persists a chart artifact version per `runComposerQueries` call and the web UI renders each inline; Slack already uses a final-answer marker (`<slack-chart versionUuid="..."/>`, `packages/backend/src/ee/services/ai/utils/slackVisualizationSelection.ts`, prompt in `packages/backend/src/ee/services/ai/prompts/systemV2.ts`) so only selected charts become cards.

Primary sources only (official docs, specs, source on GitHub). Fetched 2026-10-19. Candidates with no verifiable first-party material are listed under "Not verified".

Mechanism vocabulary: **marker** = explicit select-in-final-answer marker; **render tool** = dedicated present/render tool; **flag** = per-call display flag / audience annotation; **post-hoc** = heuristic selection after the fact; **collapse** = show everything with collapsed steps UI; **other**.

## Synthesis

Frequency of mechanisms across verified sources:

| Mechanism | Count | Where |
|---|---|---|
| Typed/flagged result (audience annotation, `purpose`, `THOUGHT`/`FINAL_RESPONSE`, `ui_component`, chart vs tool_result events) | 6 | MCP, Genie, Google CA, Cortex Agents, Vanna, (Vercel parts) |
| Dedicated render/commit step distinct from compute | 5 | MCP Apps, OpenAI Apps SDK, Claude artifacts, Claude Code artifacts, marimo |
| Explicit marker/citation in final answer | 2 (+ Lightdash Slack) | OpenAI code_interpreter citations, Anthropic `$OUTPUT_DIR` |
| Show everything, collapse/undo | 5 | Claude Code, Codex, Quick Sight scenarios, Omni, Deepnote/Hex (approval) |
| Single-result-by-construction | 3 | PandasAI, Metabase, Cortex Analyst |

Observations:
- The two production LLM platforms converge on the same shape: compute tools emit *addressable* outputs (container files, `$OUTPUT_DIR` file_ids, `structuredContent`), and surfacing is a separate model-driven act (citation annotation, copy to output dir, call the render tool). Nothing is shown merely because it was computed.
- MCP standardises the per-block version of this: `annotations.audience: ["user"]` vs `["assistant"]` on tool-result content, with `priority`. It is a hint the client honours; the spec does not mandate hiding.
- Analytics-specific APIs (Genie, Google CA, Cortex Agents) type the stream instead: thoughts/progress/tool results vs final answer / chart / table blocks, and the client renders only the "final" kinds while keeping ids for later retrieval.
- Notebook agents keep everything but gate on *commit* (marimo scratchpad vs cells, Hex confirm/undo).

Fit for Lightdash (artifacts must persist for node reuse, but not all be visible):
1. Keep persisting every `runComposerQueries` artifact version (needed as node ids; matches OpenAI containers / Anthropic container state / MCP `resource_link`).
2. Mark visibility separately from existence. Two viable shapes already present in the ecosystem:
   - **Marker in final answer** (what Slack does; same family as OpenAI `container_file_citation` and Anthropic `$OUTPUT_DIR`). Reuse `parseSlackVisualizationSelection` for web, stripping the marker before display. Cheapest and already prompt-trained.
   - **Audience flag on the tool result** (MCP `annotations.audience`): default composer results to `assistant`-only and let the model/tool flip to `user` on the final presentation call. Requires a prompt-level or arg-level signal per call; MCP Apps / OpenAI Apps SDK go further and split a `present_chart` render tool from the compute tool.
3. Regardless of selection mechanism, keep a **collapse** affordance (Claude Code `Ctrl+O`, Quick Sight blocks) so unselected artifacts stay reachable from the thread for debugging and follow-up ("show me the second one").
4. Avoid post-hoc heuristics: no verified tool picks charts by heuristic; the decision lives with the model (markers, render tool) or the user (notebook approval), never with a guess after the fact.
