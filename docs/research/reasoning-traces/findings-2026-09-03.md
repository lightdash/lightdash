# Findings: reasoning traces from real usage (2026-09-03)

First run of the spike on real data. Source: product telemetry for the Lightdash
internal organisation, 30 days to 2026-09-03, through the Analytics project's
warehouse (`extract_events_bq.sql`). The application-database route
(`extract_events.sql`) was not available: no read replica, and the local `bq`
login had expired, so the stream was pulled through the MCP `run_sql` tool in
three packed pages (`unpack_events.py`).

Short version: the path is visible, the words are not. Telemetry records that a
person iterated, re-ran, detoured to underlying data and saved, but not which
fields they touched or what they asked the agent. Read as reasoning traces, the
sample fails; read as a map of where reasoning happens, it is useful.

## What was read

| | |
|---|---|
| Events after collapsing | 18,230 |
| Users | 38 |
| Episodes (20 min gap) | 2,430 |
| Episodes with 3+ steps | 991 |
| Sample read by hand | 50 (all from the two exploration classes, by design) |

Events collapsed per user/object/minute: dashboard tile queries, metrics-catalog
previews, chart views, dashboard views. Excluded contexts: `api` (24,837 rows,
27 users; not a UI step), scheduled, embed, CLI, totals, autocomplete,
pre-aggregate materialisation.

## Episode class mix

Whole organisation, then the Analytics project alone (the internal warehouse,
where real questions get asked), then everything else (demo, staging, preview
and test projects).

| Class | All | All, 3+ steps | Analytics | Analytics, 3+ | Demo/test | Demo/test, 3+ |
|---|---|---|---|---|---|---|
| single query | 919 | 76 | 41 | 28 | 878 | 48 |
| consumption | 878 | 384 | 532 | 237 | 346 | 147 |
| agent only | 385 | 300 | 278 | 222 | 107 | 78 |
| exploration, no save | 215 | 198 | 103 | 96 | 112 | 102 |
| exploration→save | 33 | 33 | 9 | 9 | 24 | 24 |

Two things stand out before reading a single trace.

The Analytics project is agent-first. Among multi-step episodes there, the agent
(web app, Slack, MCP) accounts for 222 episodes against 105 for hand exploration.
The exploration→save loop that the original doc treats as the canonical
reasoning unit happened 9 times in 30 days on real data.

Half the "exploration" is not analysis. 29 of the 50 sampled exploration
episodes were on demo or test projects: rebuilding a sales-demo dashboard,
testing parameters in embed, duplicating a KPI dashboard, poking a data-app
visual. The internal organisation is a poor proxy for a customer organisation on
this axis, and any customer-facing dataset would need the same project-level
split.

## Could a colleague tell what the person was trying to find out?

Scored on the 50 sampled episodes, three levels:

| Verdict | Count | Where the signal came from |
|---|---|---|
| Question inferable | 2 | A saved chart whose title is the question (episodes 36, 49). Both titles are in the agent's question-as-title style. Only 49 is on real data. |
| Task inferable, not the question | 7 | Dashboard and chart titles: "Plumly Sales", "Copy of Sales Pipeline", "Test params embed", "Josh Test", "Copy of KPI dashboard", data-app viz (7, 17, 18, 20, 30, 32, 35). All demo or QA. |
| Topic only | 19 | Explore name alone: someone spent 15 minutes narrowing `ai_token_usage`, or moved `pylon_issues` → `linear_issues` → `linear_customer_requests`. What about it, unknown. |
| Nothing | 22 | Demo data churn, metrics-catalog previews, repeated dashboard reloads, two SQL-runner runs. |

So 2 of 50, and in both cases the intent was recovered from an artefact title,
never from the path. Zero episodes let a reader infer the question from the
sequence of query shapes alone.

## What the traces do show

Even with counts instead of names, four recurring shapes are legible, and each
is a candidate anchor for intent capture:

- **Narrowing.** Drop a dimension, drop a filter, re-run; repeat until the
  table is small (41: fourteen steps on one explore, ending "-1 sort"). The
  question is being sharpened, and the moment it stops is the moment to ask.
- **Detour to underlying rows.** `viewUnderlyingData` in the middle of a
  dashboard or explore run, then back to the aggregate (12, 18, 24, 43). A
  colleague would read this as "checked the number was real".
- **Agent hand-off.** An `ai` query followed within seconds by an `exploreView`
  with the same shape (5, 11, 19, 27): the person opened the agent's answer in
  the explorer and carried on by hand. The prompt is the intent; it is in the
  application database, not in telemetry.
- **Build loop.** exploreView → save chart → dashboard reload → exploreView
  (7, 49). Intent is the chart title, which is only meaningful when the author
  bothered, or when the agent wrote it as a question.

## What telemetry lacks

Verified against the raw event tables and the backend event definitions
(`packages/backend/src/analytics/LightdashAnalytics.ts`):

| Gap | Effect on a trace |
|---|---|
| `query.executed` carries `exploreName` and field *counts*, no field ids | Steps read "+1 dimension; -2 filters", never "added `orders_status`" |
| `ai_agent_prompt.created` carries ids only, no prompt text | "asks agent: ''" |
| `saved_chart_view` / `dashboard_view` names are null in the raw stream | Names had to be joined back from the charts/dashboards models (`apply_names.py`); 1,692 of 3,567 view events still unresolved |
| Chart saves carry title and chart type, no explore | Save steps cannot be tied to the query that produced them except by adjacency |
| Metrics catalog auto-runs a preview per visible metric (`metricsExplorer`, 2,811 collapsed events) | Looks like exploration, is browsing. Reclassified as neither in `sessionise.py` |
| `api` context is the single largest source (24,837 rows) with chart ids attached | Unknown mix of scripts, CLI tooling and integrations; dropped |
| The dbt model `queries` drops `explore_name` even though the raw event has it | Fixable in `analytics` with one column |

## What this implies for intent capture

1. **Telemetry cannot be the reasoning dataset.** It answers "where and how
   often does reasoning happen" but not "what was the question". The
   application database has both halves (`query_history.metric_query` with
   field ids, `ai_prompt.prompt` with the words). The spike still needs a
   read-replica connection string to run `extract_events.sql` and give a real
   answer to the 50-episode question.
2. **The agent is the cheapest intent source already in production.** In the
   Analytics project, two thirds of multi-step episodes involve the agent, and
   the two episodes where the question was recoverable both got it from an
   agent-authored title. Capturing the prompt next to the resulting query shape
   is a schema-free win.
3. **Ask at the end of a narrowing run or at save time, not on every query.**
   Narrowing runs and build loops are detectable from counts alone, so a
   prompt for "what were you checking?" can be triggered without field-level
   data. Consumption episodes (dashboard reload after reload) should never
   trigger it.
4. **Split by project before believing any mix.** Demo and test projects
   produced 24 of the 33 exploration→save episodes.

## Reproduce

```bash
# 1. Run extract_events_bq.sql through MCP run_sql with {org_uuid}/{days}
#    filled in, paging on rn (250 groups per page fit under the tool limit).
# 2. Unpack, join names, sessionise.
python3 unpack_events.py page1.json page2.json page3.json > events.tsv
python3 apply_names.py names.json < events.tsv > events_named.tsv
python3 sessionise.py events_named.tsv --gap-minutes 20 --sample 50 --out-dir out
python3 redact.py paying.json < out/episodes.md > sample-2026-09-03/episodes.md
```

`sample-2026-09-03/episodes.md` is the redacted sample that was read. Raw pages,
`events.tsv`, `episodes.jsonl` and the name lookups are not committed.
