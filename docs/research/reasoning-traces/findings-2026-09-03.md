# Findings: reasoning traces from real usage (2026-09-03)

The spike ran twice on the same 30 days of the Lightdash internal organisation:
once through product telemetry (the analytics warehouse) and once through the
application database of the `analytics` Cloud SQL instance. The second run is
the one that answers the question. The first is kept because it shows exactly
which fields make the difference.

Short version: with the application database, half the sampled exploration
episodes read as a question a colleague could state. With telemetry, two in
fifty did. The difference is named fields and prompt text, nothing else. The
path shapes (narrowing, detours, agent hand-offs, build loops) are identical in
both.

## The two routes

| | Application database | Telemetry |
|---|---|---|
| Source | `query_history`, `saved_queries_versions`, `analytics_*_views`, `ai_prompt` via cloud-sql-proxy (`run_cloud_sql.sh`) | Raw server events in BigQuery via the MCP SQL tool (`extract_events_bq.sql`) |
| Query step carries | explore, dimension and metric ids, filter fields and operators, sorts, custom fields, row count, error | explore, field counts |
| Agent prompt carries | prompt text, thread title, feedback | ids only |
| Chart save carries | title, type, explore, fields, filters | title, type |
| View events carry | chart or dashboard name | null names |
| Raw events, 30 days | 118,590 | ~60,000 query events plus views |
| After dropping `api`, `cli`, totals and collapsing tiles, previews and views per minute | 19,053 | 18,230 |
| Users | 37 | 38 |
| Episodes (20 min gap) | 1,708 | 2,430 |
| Episodes with 3+ steps | 970 | 991 |
| Sample read by hand | 50 | 50 |

The episode counts differ because the application database groups a dashboard
load into far fewer rows and its `api` context is larger (28,412 rows).

## Episode class mix, application database

Whole organisation, then the Analytics project alone (the internal warehouse,
where real questions get asked), then demo, staging, preview and test projects.

| Class | All | All, 3+ steps | Analytics, 3+ | Demo/test, 3+ |
|---|---|---|---|---|
| consumption | 985 | 382 | 238 | 144 |
| agent only | 396 | 307 | 232 | 75 |
| exploration, no save | 182 | 165 | 83 | 82 |
| single query | 99 | 70 | 29 | 41 |
| exploration→save | 46 | 46 | 18 | 28 |

Same picture as the telemetry run. The Analytics project is agent-first (232
multi-step agent episodes against 101 hand explorations), the
exploration→save loop is rare on real data (18 in 30 days), and demo projects
produce most of the saves (28 of 46).

Among the 600 multi-step Analytics episodes: 180 contain a prompt, 24 contain a
chart save, 20 contain an underlying-data detour, and 10 contain an
agent-to-explorer hand-off (an `ai` query followed within two minutes by an
explorer run of the same explore).

## Could a colleague tell what the person was trying to find out?

Fifty episodes from the two exploration classes, same sampling seed as the
telemetry run, scored on the same rubric.

| Verdict | App DB | Telemetry | What carried the signal |
|---|---|---|---|
| Question legible | 25 (18 real data, 7 demo) | 2 | Prompt text in 5; named fields and chart titles in 13; demo prompts and titles in 7 |
| Task legible, question not | 7 | 7 | Building or testing a dashboard, all demo or QA |
| Topic only | 7 | 19 | Explore name and a few fields, no clear question |
| Nothing | 11 | 22 | Auto-refresh loops, auth errors, SQL-runner runs, demo churn |

Two things made the difference, and neither is subtle.

Named fields turn a shape into a question. "count distinct `organization_id` by
`organization_type`" is the question "how many orgs are cloud versus
self-hosted". "`total_queries`, `ai_queries`, `mcp_queries` by week with custom
fields `ai_agent_share`, `mcp_share`, `human_share`" is the question the chart
title then confirms: what share of queries does the agent run. Thirteen of the
eighteen real-data yeses came from fields and titles alone, with no prompt in
the episode.

Prompt text turns a detour into a story. Episode 1: the person asks the agent
"any events on homepage-related stuff?", the agent queries page views, the
person opens the events explore and filters by event name, hits the billing cap
four times, adds organisation name, pastes the resulting URL back to the agent
("this is what i meant sorry"), then asks "wow ok who and when" and the agent
adds user name and timestamp. Every step is legible, including the dead ends.

## What the traces show

Four shapes recur, now with the nouns attached. Each is a moment where intent
could be captured cheaply.

**Narrowing.** Add a dimension, look, remove it, add a filter, re-run, until the
table says what the person wanted. Episode 42: chart views by created week and
chart type, then CLI events by month and command, a custom field for the
command's first word, an error, then the same by warehouse type. Episode 34:
deals by MRR and company, add months in pipeline, filter to won deals, three
filter operators tried in a row.

**Detour to the rows.** Underlying data opened from a chart or dashboard,
filtered to the cell the person was looking at, then back to the aggregate.
Episode 17: a support-issues chart by month and category, then the rows for one
month and one category, twice.

**Agent hand-off.** Episode 3: the person explores organisations by creation
date and type, pastes the table into the agent, asks how to tell cloud from
self-hosted, is told about `app_mode`, and asks for a hunch on one prospect.
The agent then reads the sales account record. The path moves from explorer to
agent and back with the question intact.

**Build loop.** Episode 29: open the AI usage dashboard, open the query
explore, add the three share metrics, save the chart, reload the dashboard.
Episode 36: 169 steps editing an AI token spend dashboard, each chart a
question ("Whose AI usage are we subsidising?", "Prospects with high AI usage").

## What is still missing, even with the application database

| Gap | Effect |
|---|---|
| Filter values are not extracted (only fields and operators) | "where `organization_name` equals" hides which organisation. Deliberate, to keep names out of the sample, but values are in `query_history` |
| The agent's answer text is not in the stream | Prompts read as one side of a conversation. `ai_prompt.response` exists |
| Result content is not in the stream | Row counts and errors only. Whether the number surprised the person is unknowable |
| Metrics-catalog previews and dashboard tile loads dominate raw volume | Collapsed per minute here; the same rule must run before any reading |
| Auto-refresh and QA loops look like exploration | Episodes 32 and 33: one chart re-run thirty times in an hour |
| `query_history` retention bounds the look-back | 30 days here; the setting decides |

## Implications for intent capture

1. **The application database is the reasoning dataset.** Half of sampled
   exploration on real data already reads as a question with no new capture.
   The extraction is one SQL file and a proxy; the read-replica route should
   be productised before any schema work.
2. **Field names are most of the signal.** Thirteen of eighteen real-data yeses
   needed no prompt. A model of "what question is this shape" over the semantic
   layer is a cheaper first step than asking users anything.
3. **Prompts add the why.** Thirty percent of multi-step Analytics episodes
   contain a prompt, and those are the episodes where dead ends and
   corrections are legible. Store the prompt next to the query it produced,
   and the answer next to that.
4. **Ask at narrowing's end and at save time.** Both are detectable from the
   path. The remaining 25 episodes that were not legible were mostly loops and
   demo churn, where asking would annoy.
5. **Split by project first.** Demo and test projects produced 28 of 46 saves
   and 23 of the 50 sampled episodes.

## Reproduce

```bash
gcloud auth login --update-adc
./run_cloud_sql.sh analytics <organization_uuid> 30 > events.tsv
python3 prepare_events.py < events.tsv > events_prepared.tsv
python3 sessionise.py events_prepared.tsv --gap-minutes 20 --sample 50 --out-dir out
python3 redact.py customer_names.json < out/episodes.md > sample-2026-09-03-appdb/episodes.md
```

`sample-2026-09-03-appdb/episodes.md` is the redacted sample that was read.
`sample-2026-09-03/episodes.md` is the telemetry sample for comparison. Raw
extracts, prepared streams, `episodes.jsonl` and the name lists are not
committed.
