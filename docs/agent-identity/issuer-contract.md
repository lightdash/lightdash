# Agent connection issuer contract

Passing against the HTTP double validates this design only. Run the consumer suite against the real issuer before launch.
Real approval and code creation, exchange and refresh-family persistence, crash recovery, the all-pod switch and real token separation from approval URLs remain unproved.

## Issuer requirements and settled compatibility

These requirements distinguish the issuer's obligations from the CLI's current compatibility behaviour. They do not authorise issuance. Source baseline: `dc7d0d6d68`.

1. Use `agent_connection.approved_projects: { project_uuid: string, slug: string | null }[]` in the initial token response. The issuer must include the frozen approved IDs, with approval-time slugs for slug-selected projects. The CLI verifies these against status and the requested selectors. It discards the mapping after verification. Approved IDs and actions already persist in `lastReported.approvedProjects`; no new stored field is needed. Unknown metadata and mapping properties are ignored and never saved. A supplied malformed mapping is refused. Omission remains accepted for UUID-only and all-project requests, which status can prove without a project read. Omission cannot prove a slug-only selection.
2. The issuer MUST return `agent_connection.grant_uuid` and a positive `agent_connection.grant_revision` in token metadata, and MUST return the canonical `issuer` and `resource` on initial exchange. The temporary CLI fallbacks below are not permission for a future issuer to omit these fields. Refresh metadata is currently ignored; the returned token must independently pass the real person and saved-connection status checks.
3. Require integer `refresh_expires_in` in **every** successful token response, including refresh. Use the access lifetime's existing bound, 1 through 2,147,483,647 seconds, then clip to the absolute connection expiry. On refresh, never extend the previously saved refresh deadline. A valid earlier reported family expiry can shorten the saved deadline. This is a fixed maximum refresh-family lifetime, not a sliding lifetime. Existing nullable stored deadlines remain readable; a successful refresh supplies a bounded deadline.
4. Keep unknown response properties ignored and reconstruct only known saved fields. Callback duplicates of known fields are refused. JSON decoding currently uses `response.json()`, so duplicate JSON properties use the last value, including escaped property names. The issuer must not send duplicate JSON keys. The suite pins this parser behaviour rather than claiming duplicate rejection.
5. OAuth scopes are an envelope, not approved actions: initial scopes must have valid syntax; refresh must keep exactly the saved scope set. The server must intersect that envelope with the stored per-project connection limits. `projects: null` means a finite approval-time snapshot, never a future-project wildcard.
6. Code reuse, token-family binding and separation from approval-URL values are issuer invariants. The double models refusals for invalid exchange bindings and reused codes. The CLI cannot independently prove the server's persistence or whether a different connection's token is misreported by all server endpoints. It also cannot retract an approval URL already printed before a token exists. Test these against the real issuer and database before claiming the gate is closed.

## External instance identity and proxies

The issuer and resource are the canonical external instance URL, including its
public path prefix. For `https://example.com/tools/lightdash`, both values are
`https://example.com/tools/lightdash`. The saved resource must equal the saved
instance exactly. The approval request, callback issuer and token exchange bind
to this external identity.

A proxy can strip the prefix before forwarding internally. The CLI still sends
all connection API requests to the external `<instance>/api/` paths. The internal
upstream address is not the issuer or resource. Approval and settings links use
the external instance and locally built paths. Without a usable saved connection,
a settings link is the configured URL as written with the path added.

The token endpoint must not redirect. The CLI also refuses redirects during
bootstrap, proof, refresh, status and revocation, including personal recovery.
This includes same-origin redirects and redirects that only add a slash. Serve
the final API endpoints directly. Browser sign-in navigation and the local
callback listener are separate from this API transport rule. Public asset and
external manifest downloads carry no connection credential and use their own URLs.

## Temporary CLI fallbacks

Remove these temporary fallbacks when the issuer is built. Paths below are relative to `packages/cli/src/`.

- Callback-only locator: absent token metadata can use the callback `grant_uuid`; a locator missing from both places is refused (`agentConnections/initialToken.ts:54`). A metadata-only locator also works when the callback omits the hint.
- Optional initial issuer and resource: each is checked only when supplied (`agentConnections/initialToken.ts:94`). The issuer must send both.
- Optional grant revision: absent or null revision is saved as null; a supplied non-null value must be a positive safe integer (`agentConnections/initialToken.ts:63`). No status revision comparison exists today. The issuer must send a positive revision.

## Source and evidence

The consumer suite is `packages/cli/src/agentConnections/issuerContract.test.ts`. It calls the actual connect handler, actual dual-loopback listener, initial exchange, token provider and private store. It uses a temporary HOME and real config file. Only the remote issuer is a double; console interception only observes output. It runs with non-interactive mode so the double delivers the callback over HTTP without launching a browser, including when CI is set.

The current server is `AgentConnectionApprovalService` and its approval request model. It accepts a strict request, resolves slugs as the person, binds browser review to the session, nonce and revision, seals a narrowed selection, and consumes a completion once. Today completion returns `error`, `state` and `iss`; it creates no connection, code or token. This change does not modify that code. The protected issuance test remains unchanged.

Tests below use short names that appear in the consumer suite. A passing consumer test proves local behaviour with its fixture responses. It does not prove a real approval made those responses true.

## Status and first use

Connect compares status `grantUuid`, `name` and `clientId` with the requested connection and checks approval and expiry bounds. Lifecycle status compares `grantUuid`, `name`, `clientId`, `approvedAt` and `expiresAt` with the saved slot. Provider first-use and refresh verification compare those saved fields except `name`; they do not compare the status name. Connect and provider use require `status: active`, `limitsStatus: ok` and null `revokedAt`; lifecycle status can report revoked or expired connections.

Saved timestamps use canonical millisecond UTC strings (`YYYY-MM-DDTHH:mm:ss.sssZ`). Seconds run from 00 to 59: a leap second (`:60`) is refused, because it cannot be read back as a time. `lastUsedAt` and `revokedAt` are nullable. `approvedAt` must precede grant expiry. The canonical instance and resource must match and are each at most 2048 characters. Access and non-null refresh deadlines cannot exceed grant expiry.

Each approved project has a UUID, nullable display name and distinct known `approvedCapabilities`. Approved and effective project ID sets must be equal. Each effective project has exactly those capability keys when limits are valid, each with boolean `allowed` and a known nullable `reason`; `allowed` equals whether the reason is null. Duplicate project IDs or capability keys are refused. The public report strips terminal and control characters from display names, so a sanitised name can remain non-null; unsafe names become null. Lifecycle status can instead refuse a name containing a saved token before public-report sanitisation. Unknown response fields are dropped by schema reconstruction and the public report.

At connect time, requested actions must contain every approved action. The CLI keeps the constraints-v2 per-project map rather than a union. Effective permissions may be narrower, but cannot introduce a project or action beyond that response's approved map. The issuer must freeze the true selection at approval; the CLI has no independent browser receipt to verify that initial snapshot.

Removing the project read also removes its connect-time proof that the project still exists, its current slug matches, the token is accepted for that project, and current view permission and analytics-project guards pass. The issuer must resolve and freeze slugs truthfully. A connection can now be saved for a project the person can no longer open; its effective access is then reported as false.

Today the CLI accepts a later status answer whose approved projects or actions differ from those saved at approval; this remains open and must be addressed with the first change that lets a connection be edited.

## Evidence still needed from the real issuer

- Real approval creates a fresh persisted connection and one-time code from the sealed selection, including the frozen `projects: null` snapshot and approval-time slug mapping.
- Real PKCE exchange binds code, access token and persisted refresh family to that connection, person, client and resource; refuses revoked/expired connections and replay across servers; rotation survives crashes without family widening.
- Issuing transactions recover after interruption; duplicate approval and replacement/receipt rules are safe. This suite's local store journal is not evidence of server crash recovery.
- The issuance switch honours the all-pod readiness check. No switch or issuing path is added here.
- Real code/access/refresh values neither equal nor contain any approval-URL value, including encoded, decoded and printed representations; those URL representations must not contain credentials either. Fixture separation alone proves no production entropy or generation property.
- Bind this suite to a real issuer fixture that creates and approves requests and can inject the same fault cases. Keep its real consumer calls and filesystem assertions; replace its HTTP double setup with real approval/DB controls. Add database, multi-server and crash evidence rather than claiming an unmodified HTTP-only run proves persistence.
