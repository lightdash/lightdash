# Agent connection launch measurements

These measurements use synthetic data on a development machine. Database statement counts, returned rows and bytes are the primary results. Times are indicative. No credentials are issued by approval. The decision stores an approved selection; connection rows used here are created separately through the grant model.

With three approved capabilities, a status call at 500 projects uses 12,009 read statements and returns 791,504 rows. The repeated role queries return all of the person's memberships for every selected project and capability. This gives quadratic returned-row growth when selection size and person membership count grow together.

## What was measured on

- CPU: Apple M4 Pro
- Logical CPUs: 12
- Memory: 24 GiB
- Operating system: macOS
- Node: v24.18.1
- Postgres: PostgreSQL 18.6
- Commit: d0df5ee2ee43914d3837197eabdf0029775e8476
- Date: 2026-10-12
- Warm-up runs excluded: 2
- Approved actions: read_discover, query, deploy_upload
- Dimensions per explore: 40
- Metrics per explore: 10
- Stored explores per project: 10

The machine was under load from other work during the runs.

One organization, one active verified person with an organization member role and a developer role on every project, three groups with that person in all three, and a managed agent policy allowing all capabilities for developers and restricting use to those groups. Each measured connection selects Read and discover, Query, and Deploy and upload. Each project initially stores ten synthetic explores. Project counts increase within one temporary database; the person's memberships increase with them. The 500-project control holds the person constant and selects only one project in the connection. List scenarios contain exactly the stated number of active connections.

Each explore contains 40 dimensions by default and ten metrics, compiled SQL, labels and descriptions. This is a declared medium-width synthetic model, not a sample of production data. The exact generated JSON bytes appear below. UUID inputs and field shapes are deterministic; opaque grants, approval nonces and timestamps are generated by production methods. Two warm-ups are excluded before A/B and stored-load samples. A has at least 20 measured runs; B has at least ten.

Feature-flag lookup is stubbed to enable only agent identity. Group availability is enabled and custom-role licensing is disabled. Policy, person, group, project and grant reads use real models. EXPERIMENTAL_CACHE=true enables the user and PAT caches. The session cache is primed outside each measured interval, then session deserialization calls the real warm user cache; cookie parsing, session-store reads and expiry writes are excluded. PAT authentication and bearer authentication run through the registered middleware. The production controller and project-read service method handle GET /api/v1/projects/{projectUuid}. A query-style endpoint and warehouse execution are not measured. Bearer measurements wait for the real asynchronous last-used update before removing listeners, to keep that write with its request. Timings include listener bookkeeping and decoded-row serialization; integer bigint values are counted as decimal strings.

## What grows with what

- A: the connection request uses 20 reads / 135 returned rows with 50 person projects and 20 reads / 1035 rows with 500. Holding the person at 500 projects, the one-project grant uses 20 reads / 1035 rows versus 20 reads / 1035 for the 500-project grant. SQL count is constant; fresh-person rows grow with memberships and grant bytes grow with selection.
- B approval: 66 reads at 50 projects and 66 at 500; returned rows grow from 1673 to 16073. The query count is constant in these runs.
- B status: 1209 reads at 50 and 12009 at 500. Status repeats policy checks for each approved project and capability; its read count grows linearly for this fixed three-capability shape. Returned rows grow from 11654 to 791504: every repeated role lookup returns all of the person's project memberships. This is quadratic in N when both the selection and the person's memberships grow to N; more generally the repeated membership rows grow with selected projects times person memberships times capabilities.
- B storage: constraints text grows from 4289 bytes at 50 to 42539 at 500. Logical size is linear in project selection; PostgreSQL compression changes stored datum growth.
- B list: at 500 projects, one connection returns 71834 response bytes with 9 reads; 50 connections return 3589299 bytes with 9 reads. Response bytes grow with projects times connections while read count stays fixed. request project resolution and list project naming both search an array for each selected project, giving a quadratic comparison bound when organization size grows with selection. The timings alone do not establish a quadratic runtime curve.
- C: each summary query returns one row / 96 decoded bytes at all four sizes. PostgreSQL still inspects all stored explores; operation guard counts are constant in project size.
- D: buffered retained heap grows from 2328496 bytes at 100 explores to 43861408 at 2000. The helper retains the whole input array; the ordinary consumer receives its first explore after one production step, independent of total input size.

## What the numbers do not show

This is not production hardware or a production-size sample. It excludes remote network latency, concurrent workload control, cold caches, real explore-size distributions and database query-plan scanned rows. Other work ran on the machine during these measurements, so times are indicative. Warm session-store costs and feature-flag resolution are excluded. Only three approved capabilities and one direct project role are modeled; other policy/role shapes can change the counts. C substitutes compiler and downstream sinks and stops virtual-view writes after their guard; D isolates one buffer helper, not whole-compile peak memory. PostgreSQL datum sizes do not measure total disk allocation.

## Re-run

From the repository root, with installed dependencies and built common, formula, warehouses and visualization packages:

```sh
python3 packages/backend/src/database/migrations/__tests__/launch-measurements/run.py --json /absolute/path/results.json --markdown /absolute/path/results.md
```

To compare a second clean run, add --compare /absolute/path/first-results.json with a different --json output. It fails if statement or returned-row counts differ and appends the comparison result to the report.

The launcher reads ldenv-pg's password in memory and uses its localhost:15432 server unless PGHOST is supplied. For another server set PGHOST, PGPORT, PGUSER, PGPASSWORD and PGDATABASE. createMigratedDatabase creates and drops a uniquely named database cloned from the repository's migrated template. No existing application database is read or written. The template may need its initial migration build.

Sizes: MEASURE_PROJECT_SIZES=1,50,200,500,1000; MEASURE_LIST_SIZES=1,10,50; MEASURE_EXPLORE_SIZES=10,100,500,2000; MEASURE_COMPILE_SIZES=100,500,2000; MEASURE_DIMENSIONS=40. Repetitions: MEASURE_REQUEST_RUNS=20 and MEASURE_APPROVAL_RUNS=10 (do not lower these for a gate run). For the default sizes, expect about three minutes on this machine with the existing migrated template; initial migrations can take longer. Output includes six adjacent isolated-memory JSON files. The database phase took 130.29 seconds; allow additional time for six fresh memory forks and initial migration setup.

The harness uses a dedicated measurement.config.ts and launch.measurement.ts under src/database/migrations/**tests**/launch-measurements. The backend production build excludes src/\*_/**tests**. Normal unit CI selects _.test.ts; schema-compatibility CI selects _.migration.integration.ts under migration folders and one explicitly named membership test. Neither selects this harness. Other integration configs also do not select _.measurement.ts. The launcher and measurement test both refuse CI=true. No package command or CI workflow changes are required.

## Repeatability

Two full runs each used a new temporary database. All SQL statement counts, returned-row counts and per-statement counts matched across A, B and C. Times, response dates, nonce values, PostgreSQL compressed datum sizes and heap/RSS samples can differ. The first raw run is retained beside the final results. The stored-explore arm (C) was rerun on its own on 2026-10-13, before and after the load reduction; that rerun is not part of this two-run comparison.
