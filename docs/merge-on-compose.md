# Merge-on-compose

How merged visualizations execute behind the `merge-on-compose` feature flag, what still runs warehouse-side, and what it takes to retire the warehouse merge path. Companion to the merge compilation pipeline (`compileMergeQuery`, `MergeQueryBuilder`) and the compose engine (`executeAsyncComposeSqlQuery`).

## The two engines

A merge joins two aggregated queries on a shared key. There are two ways to execute one:

- **Warehouse merge** (the original): both sources compile as CTEs of one statement in the project warehouse's dialect — per-dialect `FULL OUTER JOIN` handling, typed null placeholders, an in-SQL truncation guard — and that statement runs on the warehouse.
- **Compose merge** (`merge-on-compose`): each metric source runs as its own metric query (its own access rules, required filters, and the metric-query result cache), and the DuckDB compose engine joins the materialized results, bound as typed `read_json` reference CTEs over the S3 result files.

The join is generated by the **same `MergeQueryBuilder`** in both modes — the compose mode instantiates it with the DuckDB sql builder over `SELECT * FROM merge_source_N` reference tables (`buildComposeMergeSql`), and the null-placeholder/string-cast derivation is shared (`getMergeJoinKeySqlOptions`). Join semantics agree by construction, not by parallel implementations. The pivot stage and terminal wrapper also flow through the shared `MergeQueryComposer` seam, and result streaming inherits the merge-guard consumption (`consumeMergeResultMetadata`), so truncation refusal behaves identically.

## Routing and fallback

`executeAsyncMergeQueryInternal` routes per submission:

| Condition | Engine |
| --- | --- |
| Flag off | Warehouse merge |
| Compose engine unavailable (`createExecutionWarehouseClient` throws) | Warehouse merge |
| Flag on, engine available | Compose merge (pivoted or flat) |
| Merge references existing query results (`{ id, queryUuid }` sources) and compose is unavailable | **Refused** with `compose_required` — there is no warehouse statement for a result source |

The fallback is a migration state, not a capability matrix: once the cutover criteria below are met, the warehouse merge path is deleted, not kept as a second engine.

## What compose mode adds

- **Result reuse**: merge sources may be existing query results (`{ id, queryUuid }`), joined as the rows they already hold — merging two visualizations that just rendered re-runs nothing and costs one `query_history` row. References are creator-scoped, must be READY and unexpired (`result_source_unavailable` names the remedy otherwise), and stored table calculations join as materialized values by design.
- **Leg caching**: metric-source legs go through the ordinary metric-query cache, so a repeated merge with warm legs skips the warehouse.
- **One join dialect**: the per-warehouse `FULL OUTER JOIN` workarounds (merge-joinable conditions, temporal `COALESCE` casts per dialect) do not exist in compose mode.

## Known engine differences

- **Raw numeric representation** normalizes to JSON numbers on the compose engine. Warehouse drivers differ (Postgres stringifies bigints and numerics; BigQuery returns numbers); DuckDB returns numbers everywhere. Values are equal; the spelling changes on warehouses that stringified. Formatted values are unchanged. The parity suite compares numerically for this reason.
- **Latency shape**: cold legs cost two warehouse round-trips plus S3 materialization plus the join, instead of one round-trip; warm or reused legs cost less than either. Chart-sized results dominate merge traffic, where the difference is small.

## Verification

- `packages/backend/src/utils/QueryBuilder/composeMergeSql.test.ts` executes the generated join on a real in-memory DuckDB: join types, typed null-key matching, string casts, truncation, limits, merge table calculations, and an indexed pivot.
- `packages/api-tests/tests/mergeQuery.test.ts` is the engine-independent parity bar: merged values must equal what each source query returns on its own, per join type, per warehouse — the same assertions run whichever engine the flag picks, and the suite covers the result-source contracts (`compose_required`, `result_source_unavailable`) adaptively.

## Rollout

1. **Dark** (today): flag off by default. Preview environments force-enable all non-excluded flags, so previews run compose merges as soon as this lands — that is the dogfood step; add the flag to `PREVIEW_EXCLUDED_FEATURE_FLAGS` to opt previews out instead.
2. **Cutover criteria**: the merge api-test suite green on every credentialed warehouse with the flag on; no compose-attributed merge regressions in preview/cloud telemetry over a release cycle; a product decision on the remaining open question — whether the compose engine (EE DuckDB) becomes a baseline dependency for merges on self-hosted, since instances without it keep warehouse merges and never get result reuse.
3. **Deletion**: remove the flag, the warehouse routing branch, and the per-dialect merge SQL surface (`executeCompiledAsyncMergeQuery` and the warehouse-dialect emission in `compileMergeQuery`). Result-source merges stop needing the `compose_required` refusal path on instances with the engine.

Never keep both engines past cutover: two merge engines with subtly different semantics is worse than either alone.
